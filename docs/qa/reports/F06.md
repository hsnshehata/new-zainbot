## 3. RECOMMENDATION: CLOSE with reason (no second extraction)

The plan bars splitting "for file size alone" — no candidate clears that bar:

1. **Nothing remaining dominates like council did.** Council was a ~35KB-raw monolith with its own polling lifecycle; the largest lazy-eligible chunk now (admin-console, 8.2KB gzip ≈ 9% of the file, ≈7% of initial eager JS) would yield roughly a THIRD of F05's banked gain, at full F04-scale cost (characterize → eager → lazy on superadmin code under active E03/C04e/D locks).
2. **inbox/training (~3.3KB each) are below the threshold where deferral pays.** An extra script round-trip on first open of a first-order tab costs more perceived latency than ~3KB saves. Deferring them would be optimization theater.
3. **orders/agents/notifications are core-tab code.** Deferral hurts the default user journey; extraction risk (live locks, D-contracts) is disproportionate to 6–8% file shares.
4. **The actual dominant weight — dictionaries, 42% — is not lazy-eligible** (first paint renders from them) and lives under C locks. F-splitting cannot touch it. Observation for C (no F action): esbuild still warns on duplicate `idea_status_*` keys — a dictionary-dedupe pass would shrink the single biggest contributor more than any lazy slice; offered as a C-track note, not a directive.
5. **Gains already banked suffice for this plan wave:** F05 −20.8KB initial, F07 −10.5% gzip. No `main=100KB` promise was ever made, and none is made now.

Conditional (recorded, not actioned): IF a future product decision wants superadmin-shell deferral, the scoped subplan is admin-console via the proven F04 pattern (characterize state/deps/callbacks → eager → lazy with shared LOCKs) — estimated ≈6–7KB gzip off initial for ordinary users. Not now.
